    Newport graphics board (overview)¶

    Intro: the Indy "XL" graphics board on GIO64 slot 0 (phys 0x1f000000; REX3 registers at 0x1f0f0000). Henry runs it on silicon as an ARM-served device: the PL captures every REX3 access into a ring and the Zynq ARM runs a software model of the board, and IRIX reaches the 4Dwm desktop. See Newport on henry for the design, screenshots and known issues. The pages in this section describe the SGI hardware.

    IRIX 6.5 4Dwm on henry (Ultra96-v2), Newport served by the ARM; Doom in a window.

    Software side: what IRIX's Xsgi, ng1 kernel driver and GL libraries actually do to this hardware (store widths, polling, pixel DMA, context switch) is in How IRIX drives Newport.

    The Indy had two graphics options. This page covers XL / Newport (host geometry, raster-only). The other was Express / XZ — a hardware-geometry pipeline (SIMD Geometry Engines + a hyper-pipelined Raster Engine); see Express / XZ. For a Henry graphics path, Newport is the far smaller target — Express adds a microcoded SIMD FP array and a command-FIFO front-end on top of a REX3-class rasterizer.

    Newport is the entry-level (8-bit, upgradable to 24-bit) framebuffer graphics board for the SGI Indy. SGI's own tagline for it was "the least graphics you'll ever need." There is no geometry/transform ASIC — the host MIPS FPU is the geometry engine, and Z-buffering lives in host system memory. The board is purely a 2D raster engine plus a framebuffer and the video-output backend. That makes it a smaller (but still large) target than a full GE-class SGI pipe: the bulk of the work is REX3's drawing command set, not a 3D pipeline.

    Board architecture¶

    Five ASIC types (plus VRAM, a colormap SRAM, and an external RAMDAC) form a one-way pixel pipeline from the host bus to the CRT. REX3 is the only host-facing chip; everything downstream is display/scanout.

    flowchart LR
    HOST([host]) -->|"GIO64 slot 0 · 0x1f00_0000"| REX3["<b>REX3</b><br/>raster engine"]
    REX3 -->|"draw / writes"| RB2["<b>RB2</b><br/>fmt + logic-op"]
    RB2 <--> VRAM[("VRAM frame buffer<br/>(8-way interleave)")]
    VRAM -->|scanout| RO1["<b>RO1</b><br/>raster output<br/>reorg / rotate"]
    RO1 --> XMAP9["<b>XMAP9</b><br/>pixel mode / mux"]
    XMAP9 --> CMAP[("CMAP<br/>colormap SRAM")]
    CMAP --> RAMDAC["RAMDAC<br/>gamma + DAC"]
    RAMDAC -->|"R / G / B"| CRT([CRT])
    REX3 -.->|"DCB"| VC2["<b>VC2</b><br/>video timing + cursor"]
    VC2 -.->|"cursor · DID"| XMAP9
    VC2 -.->|"video timing"| RO1

    Flow: host → REX3 (programs primitives over GIO64) → framebuffer (REX3 reads/writes VRAM through RB2, which holds the read/write formatters + LogicOp) → RO1 (reads the VRAM serial/video ports, merges overlay+color, undoes REX3's scanline stagger) → XMAP9 (selects pixel mode: RGB vs color-index, picks the display ID) → CMAP (colormap SRAM, in CI mode) → RAMDAC (gamma + analog RGB) → CRT. VC2 sits to the side as the video-timing/cursor/DID generator, driving sync/blank timing and the per-pixel cursor + display-ID streams (to XMAP9); it is not in the pixel datapath but gates it. REX3 owns the Display Control Bus (DCB), an 8-bit side channel it uses to program VC2/XMAP9/RAMDAC (and read back).

    Address & host interface¶

    Newport is the GIO64 slot-0 device, based at phys 0x1f000000 (4 MB aperture). REX3 is the only host-programmable chip: it is a GIO64 bus slave whose registers sit at slot base + 0xF0000 (0x1f0f0000; rex3.pdf p.20 gives the base as 0x1FnF0000, and MAME maps 0x1f0f0000–0x1f0f1fff). Pixel PIO/DMA goes through the HOSTRW registers, not a separate memory window. REX3 forwards config to the rest of the board over the DCB. The GIO bus interface runs at 33 MHz behind a 64-wide × 32-deep host FIFO; the framebuffer side is an 8-way interleaved VRAM running at 66 MHz.

    Detection. Newport has no GIO64 Product Identification Word at its slot base. Linux (arch/mips/sgi-ip22/ip22-gio.c) first checks for Express (HQ2 MYSTERY register at slot + 0x6A07C reading 0xDEADBEEF), then for a product-ID word, and finally treats a readable REX3 USER_STATUS (slot + 0xF133C) as "Newport present". How IRIX's own ng1 driver probes is not documented here. See ../peripherals/gio64.md for the GIO64 slot/address map.

    Henry relevance¶

    Implementation: an ARM-served model, working on silicon. No Newport chip is built in the PL. rtl/gio_window.sv turns every access to the REX3 window (0x1f0f0000–0x1f0f1fff) into a record in a DDR capture ring, and holds loads until the ARM answers. On the Zynq ARM, the driver runs sgi_newport (a condensed MAME newport.cpp, shared with indysim) and shows the framebuffer on an X display viewed over VNC. The MC's graphics DMA (VDMA, memory → GIO) is a channel of henry's DMA engine and feeds the same ring. The vertical-retrace interrupt is an ARM-driven INT3 local1 level. Details: Newport on henry.

    Why this split: the 2026-10-02 feasibility study (NEWPORT_FEASIBILITY.md, QEMU traces of IRIX 6.5) found IRIX's stream is ~99.9% posted writes. Serving every access on the ARM was 3–10× too slow, a REX3 rasterizer in the PL did not fit henry's LUT budget, and the hybrid (PL logs writes, ARM draws) was feasible. Any design needed MC graphics DMA and a retrace interrupt; henry has both.

    What the generic Newport work turned out to be (in the order it was needed):

    1. The probe: a readable REX3 window → hinv reports "Graphics board: Indy 8-bit" (or 24-bit).
    2. The REX3 register file, the DCB devices (VC2, XMAP9, CMAP, RAMDAC) with correct readback, and the drawing command set (spans, lines, blocks, host data). This comes from MAME's model. Two bugs that MAME has, CID match in CLIPMODE and per-plane write masks, showed up only once a real desktop ran (see Newport on henry).
    3. Scanout is not rebuilt as chips: the ARM reads the framebuffer directly and applies the CMAP/XMAP9 mode state.
    4. MC VDMA and the retrace interrupt.
